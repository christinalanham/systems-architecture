# systems-architecture

Architecture Decision Records, system design patterns, and engineering org frameworks from 15+ years of enterprise systems work.

## Why this exists

Most architecture documentation lives inside the systems it describes — buried in Confluence, locked in a company's internal repos, or never written down at all. This repo is the portable version: the reasoning, the frameworks, and the decision patterns that travel with the architect, not with the employer.

Everything here is abstracted from real work but stripped of anything proprietary. The problems are real. The constraints are real. The names are not.

## What's here

```
systems-architecture/
├── adrs/           Architecture Decision Records — documented technology choices with context and consequences
├── system-design/  System design documents and patterns for common enterprise problems
└── diagrams/       Source files for architecture diagrams (Mermaid)
```

## How to use it

These documents are meant to be read, adapted, and argued with. An ADR that fits your situation exactly is rare — but one that documents a similar tradeoff in a comparable context is useful as a starting point or a sanity check.

If you're evaluating a similar decision and want to talk through it, reach out on [LinkedIn](https://linkedin.com/in/christinalanham).

## A note on sanitization

All examples in this repo use fictional company names, system names, and data. Nothing here reflects proprietary configurations, client implementations, or employer-specific architecture. Where real technology names appear (Salesforce, NetSuite, etc.), they describe the *category* of system involved, not a specific org or implementation.
